# 自带密钥按部署 ID 保存，而不是按服务器地址

ADR-0017 让用户的 API key 只留在客户端。原生 Android 客户端把它加密存在设备的
Android Keystore 里，最初按「服务器地址 + 用户」隔离：地址是 `host:port`，换 Wi-Fi、
换域名或换 IP 之后就是另一台服务器，App 读不到原来的 key，用户看起来像丢了密钥。

地址不是部署的身份。同一个后端换地址（局域网换网段、绑定域名、反向代理迁移）仍然是
同一套数据库和同一批用户，密钥应该跟着部署走；而切换到另一个部署时，密钥又绝不能
被带过去。

## 决定

- 后端在数据库里保存一个只生成一次的随机 `deployment_id`，通过公开的 `/api/health`
  返回。它随数据库备份和恢复一起走。
- 原生客户端在每次连接和启动时读取 `/api/health`，把自带密钥按
  `own_keys.<deployment_id>.<user_id>` 加密保存。地址变化不影响读取。
- 旧版客户端按 `own_keys.<host:port>.<user_id>` 存下的数据，在仍连接同一地址时自动
  复制到部署命名空间；退出登录时两处都清掉。
- 后端不返回 `deployment_id` 时（旧版后端），客户端退回按地址保存，保持兼容。
- 网页前端仍然按浏览器 origin 隔离（localStorage / IndexedDB），不在这个决定范围内。

## Considered Options

- **按用户 ID 保存**：换部署后会把上一台的 key 发给新部署，不能接受。
- **换服务器时弹窗复制密钥**：能解决当前问题，但每次都要用户确认，而且仍然无法判断
  两个地址是不是同一个部署；部署 ID 是更可靠的判断依据。
- **用域名固定地址**：要求每个部署都配稳定域名，局域网调试和换 IP 时仍然会丢；不能
  替代客户端的存储键。

## Consequences

- 同一个部署换 IP、域名或反向代理地址，原生客户端的自带密钥不需要重填。
- 切换到另一个部署仍然隔离，key 不会跨部署发送。
- 升级前已经按旧地址保存、且之后没有再连回旧地址的密钥无法自动归属到部署；用户需要
  重填一次，之后地址再变就不会丢。
- `/api/health` 多返回一个公开的随机 ID；它不是密钥，不授权任何操作。
- 数据库新增 `deployment` 表，属于部署自身的数据，删除用户时不动它。
