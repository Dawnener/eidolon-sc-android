# 搭话推送用前台服务维持 SSE 长连接

小米推送只对企业开发者开放，个人无法注册；FCM 依赖手机稳定连上 Google。用户又明确不
接受无障碍服务的保活方式。这个决定用一个 `remoteMessaging` 类型的前台服务维持一条到
后端的 SSE 连接，尽量把耗电压到最低，并在设置里给出推送开关。

## 决定

- 后端新增 `PushHub` 和 `GET /api/push/stream`（SSE，session cookie 鉴权）；搭话成功写入
  后向该用户的所有连接发布一条事件，不落库、不重放。
- 原生客户端用前台服务（`foregroundServiceType="remoteMessaging"`）维持 SSE；系统要求
  前台服务显示一条通知，这条通知用 `IMPORTANCE_MIN`、静音、不显示时间，尽量不打扰。
- 设置里的「推送」开关默认关；关掉立即停止服务并断开连接。只有「允许推送 + 已登录」时
  服务才运行。
- 断线按指数退避重连（1 秒到 60 秒）；服务器每 50 秒发一次 SSE 心跳，避免代理断开，
  同时避免更频繁地唤醒手机；不使用轮询、不持有 WakeLock。
- 开机后如果开关是开的，`BOOT_COMPLETED` 接收器拉起服务；MIUI 还需要允许自启动和
  把省电策略设为「无限制」。
- 通知点开进入对应角色的对话；通知正文只写角色名和「她给你发来一条消息」。

## Considered Options

- **无障碍服务保活**：可以完全隐藏常驻通知，但需要用户授予高敏感权限，用途也不符合
  无障碍的设计；用户放弃了这个方案。
- **WorkManager 定时轮询**：没有常驻通知，但最短 15 分钟且 MIUI 会进一步延迟，实时性差。
- **自建 ntfy / 第三方中转**：通知来自另一个 App，不如原生体验，也仍需要另一个常驻服务。
- **FCM**：最省电，但依赖 Google 服务；本项目选择不依赖它。

## Consequences

- 会有一条低优先级常驻通知；这是 Android 对前台服务的硬性要求，无法完全去掉。
- 用户需要在 MIUI 上允许自启动、把省电策略设为「无限制」，否则系统仍可能杀掉服务；
  被杀后系统会尝试按 `START_STICKY` 重启，但不保证。
- 断网、进程被杀或服务被限制时收不到通知；打开 App 后仍能在对话和列表里看到搭话。
- 一条空闲长连接加 50 秒一次心跳，CPU 和流量都很小；耗电主要来自保持网络唤醒。
- 服务器是单进程，`PushHub` 只在内存里；服务器重启会让客户端重连，错过的通知不补发。
- 以后如果拿到 FCM 或厂商推送，可以保留这个开关，把长连接作为可选通道。
